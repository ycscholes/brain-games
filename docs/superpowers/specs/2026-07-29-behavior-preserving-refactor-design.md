# 行为保持型全仓重构设计

## 目标

在不改变游戏规则、积分换算、训练记录、闯关协议、路由和既有视觉设计的前提下，降低页面复杂度并增强本地数据与异步计时的健壮性。另行产出一份游戏体验与页面交互的修改建议；该建议不包含在本次代码行为变更中。

## 非目标

- 不调整题目生成、计分、难度、积分上限或宠物经济。
- 不修改训练记录的字段、存储键或历史兼容策略。
- 不改变 `completeGauntletLegIfNeeded()` 的返回语义或各游戏的闯关预设。
- 不进行视觉重设计、文案改版或依赖升级。

## 方案比较

### 方案 A：分层保守重构（采用）

先为当前行为建立回归测试，再提取纯函数、缓存读取与局部视图组件。只有在调用约定完全一致时才复用计时器清理能力；游戏结算仍留在各页。

优点是回归范围可审计，并能逐步验证。缺点是不会形成一个覆盖所有游戏的统一页面框架。

### 方案 B：统一游戏页面框架

把计时、状态、结算和视图全部纳入通用框架。

该方案重复度低，但会耦合不同游戏的失败条件、积分策略和闯关返回协议，超出本次零行为变更的风险预算。

### 方案 C：只修单点缺陷

仅修复逆向猜拳缓存解析和 README。

风险最低，但不能解决 `bird-count` 及多个页面的结构性维护成本。

## 设计

### 1. 本地持久化健壮性

将逆向猜拳的最高分读取提取为可测试的纯读取函数。它必须：

1. 接受空值、无效 JSON、缺失或非数值 `score`。
2. 在任何无效输入下返回 `null`，让 UI 继续显示 `0` 分。
3. 对有效的既有最高分 JSON 保持原有读取和更新行为。

不迁移现有存储键，也不删除坏数据；这避免清理操作本身成为额外副作用。

### 2. Farm Count 页面拆分

`src/pages/bird-count/index.tsx` 保持为状态编排与公共积分/闯关边界，拆出三个无业务副作用的展示组件：开始设置、进行中场景和结算结果。速度清点与农场进出各自的展示分支留在对应子组件中。

计时器注册、取消和组件卸载清理由一个局部 hook 管理。hook 的接口保持为“调度回调并返回清理能力”；它不能改变延迟值、回调顺序或回答后的状态迁移。预加载取消标识、`finishedRef` 和积分结算顺序均保留在页面编排层。

### 3. 跨页面计时器审查

对所有使用延迟计时器的游戏页进行只读审查，按以下条件分级：

- 已有卸载清理且没有悬挂状态更新：不改动。
- 缺少可验证清理：补充最小局部清理和测试。
- 与 Farm Count 相同的多计时器队列模式：仅在回调与取消语义相同的情况下复用 hook。

不会把 `setInterval`、动画帧或游戏特有倒计时强行纳入同一抽象。

### 4. 文档一致性

README 的游戏表以 `src/config/gameCatalog.ts` 为当前目录事实来源进行补全。新增针对 README 标题与当前公开目录项的轻量测试，避免新游戏合入后总览缺项。

### 5. 游戏体验与页面交互建议

新增 `docs/reviews/2026-07-29-game-experience-ui-recommendations.md`，只记录建议，不改运行代码。它按首页/全部游戏、开始页、游戏中、结算页和横向可用性五个部分，提供问题、影响、建议、优先级与验收信号。
